# 성능·안정성 실측

관련 이슈: #63 (요구사항 EVT-002, OFF-003~010, OPS-009~012)

모든 수치는 **Raspberry Pi 5(arm64, 4코어) + USB SSD**에서 운영 Compose(Caddy proxy·서버·웹·PostgreSQL 17)를 새 볼륨으로 띄워 잰 값입니다(2026-10-24). 이벤트는 합성 데이터만 씁니다.

## 도구

| 도구 | 하는 일 |
|---|---|
| `tests/load/run.sh <서버 이미지> <웹 이미지> [인자]` | 스택 생성 → bootstrap 관리자 → 부하 실행 → 컨테이너 CPU·메모리 표본 → 정리 |
| `tests/load/office_load.py` | 장치 N대·세션 M개(리드 + 하위 K명). 라운드마다 장치당 배치 1개로 모든 에이전트가 활동을 바꾸고, WebSocket 증분에 전부 보일 때까지를 **표시 지연**으로 잼 |
| `RESTART_AFTER=<초>` | 부하 중 서버 컨테이너 재시작(장애 주입) |
| `FPS_SECONDS=<초>` | 부하 중 Playwright Chromium(헤드리스, SwiftShader WebGL)으로 실시간 사무실 FPS 측정(`tests/load/fps.mjs`) |
| `tests/e2e/run.sh` | 실제 브라우저로 설치 마법사·사무실·관리·팀·로그인 흐름 확인(CI `E2E (browser)` 작업) |

## 결과(30세션 · 에이전트 90명 · 2초마다 90개 이벤트)

| 항목 | 목표 | 결과 | 비고 |
|---|---|---|---|
| 표시 지연 P95 | 2초 | **1.45초**(p50 1.22, 최대 1.50) | WebSocket 주기 0.5초. 1초 주기에서는 p95 1.67~2.05초로 목표 경계라 0.5초로 낮춤 |
| 수집 응답 P95 | — | 1.04초(라운드의 배치 3개가 모두 응답) | 서버 CPU 최대 약 120%(4코어 중), 메모리 약 95MB |
| 누락·실패 | 0 | 0 | 60라운드, 배치 실패 0 |
| 서버 재시작 회복 | — | WebSocket 재연결 **3.4초**, 배치 손실 0, 재시작 라운드만 지연 4.6초 | 부하 생성기는 Collector처럼 재시도 |
| 브라우저 FPS | 30 | **평균 39.8, 하위 5% 29.9** | 같은 Pi에서 부하와 브라우저를 함께 돌린 최악 조건. 이때 표시 지연 p95는 2.6초로 올라감(브라우저가 CPU를 나눠 씀) |
| PostgreSQL | — | CPU 최대 약 35%, 메모리 약 45MB | |

### 발견해 반영한 것

- 처음 부하 생성기가 세션마다 배치를 따로 보내 장치당 초당 5건이 되면서 **장치별 속도 제한(분당 120건)에 20% 걸렸습니다.** 실제 Collector는 장치의 이벤트를 배치 하나로 묶어 보내므로 생성기를 그 방식으로 고쳤고, 제한값은 그대로 둡니다(Collector 배치 주기 2초면 분당 30건).
- WebSocket 주기를 1초에서 0.5초로 낮췄습니다. 연결마다 조회가 2배가 되지만 Pi·소규모 사용자 기준에서 CPU 증가는 측정 범위 안이었습니다.

## 장시간

72시간 목표 중 아래만 실측했습니다. 72시간은 같은 명령에 `--rounds 129600`(2초 간격)으로 돌립니다.

| 기간 | 결과 |
|---|---|
| 1시간(1,800라운드, 이벤트 약 16만 개) | 배치 실패 0, 누락 라운드 0, WebSocket 끊김 0. 서버 메모리 91→97MB(누수 징후 없음), PostgreSQL 30→102MB(캐시). **표시 지연 p50 1.32초, p95 2.73초, 최대 3.99초 / 수집 p95 2.64초** |

1시간 실행의 p95는 목표(2초)를 넘었습니다. 같은 시간대에 같은 Pi에서 브라우저 E2E와 다른 작업의 Go·Wails 빌드가 함께 돌아 CPU 경합이 있었습니다(부하 평균 5~6). 경합인지 데이터 증가에 따른 저하인지 가르려고 부하 도구가 처음·마지막 10% 라운드의 p95를 따로 내도록 했습니다(`display_p95_first_10pct`·`display_p95_last_10pct`). 경합 없는 장시간 재측정과 72시간 실행은 남은 작업입니다.

### SLO 조정 제안

| 조건 | 표시 지연 P95 |
|---|---|
| 정상 상태(Pi 5 + SSD, 30세션·90에이전트, 다른 무거운 작업 없음) | 2초 이하(실측 1.45초) |
| 같은 호스트에서 빌드·브라우저 등 경합 | 3초 이하(실측 2.73초) |

Pi는 서버 전용으로 쓰고 빌드·브라우저는 다른 장비에서 돌리는 것을 권장합니다.

## 한계

- 브라우저 FPS는 헤드리스 SwiftShader(소프트웨어 WebGL) 기준입니다. 실제 GPU가 있는 PC 브라우저는 더 높을 것으로 보이나 측정하지 않았습니다.
- 부하 생성기와 서버가 같은 Pi에서 돕니다(네트워크 지연 없음). Tailscale·Cloudflare 경유 지연은 포함하지 않았습니다.
- 네트워크 단절은 서버 재시작으로만 주입했습니다(Collector 오프라인 큐 동작은 #33 테스트).
